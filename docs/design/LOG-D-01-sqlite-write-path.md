# LOG-D-01: Запись в SQLite

**Статус:** реализован (07.10.2026)  ·  **Задачи:** LOG-BL-04, LOG-BL-03, LOG-BL-08

## Задача

Подробный журнал в базе не должен замедлять тест в разы и должен пережить то, ради чего его включают, —
падение программы.

## Что измерено и проверено (07.10.2026, MT5 6231, Windows в WinBoat, 2 vCPU)

| Режим | мкс на запись |
|---|---|
| прежний: `synchronous = FULL`, 4 индекса, коммит на запись | 1 670 |
| `NORMAL`, 4 индекса, коммит на запись | 218 |
| `NORMAL`, без индексов, коммит на запись | 106 |
| то же, подготовленный запрос | 85 |
| `NORMAL`, 4 индекса, пакет 100 | 53 (подготовленный — 30) |
| `NORMAL`, без индексов, пакет 100, подготовленный | 13 |

- **Критическая ошибка программы** (`array out of range`): деструкторы не вызываются. Пакетный режим — из 5
  записей в базе 0. Режим «по записи» — все записи на месте.
- **Подготовленный запрос портит `_LastError`**: `DatabaseRead()` после `INSERT` оставляет код 5126, то есть
  логирование стирало бы код ошибки вызывающего (`logger.Info(...); int e = GetLastError();`).
- База MT5 работает в режиме WAL; `PRAGMA synchronous` нельзя менять внутри транзакции.
- Два обработчика на одном файле в режиме «по записи» — 40 записей из 40 без ошибок.

## Решение

1. **Режим по умолчанию — «по записи»** (каждая запись — своя транзакция) и `synchronous = NORMAL`: запись
   переживает критическую ошибку программы и снятие терминала; потерять её можно только при отключении питания.
   `SetDurable(true)` возвращает `FULL`.
2. **Пакетный режим** (`auto_commit = false`) остаётся для случаев, где важна скорость; в описании класса сказано,
   что при критической ошибке хвост теряется.
3. **Запрос — текстом** (`DatabaseExecute`), не подготовленный: 20 мкс не стоят испорченного `_LastError`.
4. **Индексы не создаются при записи**: `SetCreateIndexes(true)` / `CreateIndexes()` — перед разбором журнала.
   В существующих базах индексы остаются.
5. **Таблица**: добавлены `time_local`, `elapsed_us`, `seq` (LOG-D-02); в таблицу прежней версии столбцы
   добавляются при открытии (`ALTER TABLE … ADD COLUMN`), старые строки остаются с `NULL`.
6. **Сбой записи**: одна строка в журнал терминала, дальше — счётчик `FailedCount()`.

## Что рассмотрено и отвергнуто

- **Очередь записей в памяти и короткие транзакции** — при критической ошибке теряет то же, что пакет, и сложнее.
- **Коммит по времени** — проверять время можно только на следующей записи; при падении не помогает.
- **Немедленный коммит записей `ERROR` и выше в пакетном режиме** — критическая ошибка сама записи не порождает,
  причина остаётся в незакоммиченном хвосте.
- **`synchronous = OFF`** — выигрыша против `NORMAL` в WAL нет (128 против 209 мкс при индексах — в пределах шума
  замера), риск повреждения базы при сбое питания.

## Совместимость

- Сигнатуры конструктора и методов прежние; добавлены `SetDurable`, `IsOpen`, `FailedCount`, открытый
  `CreateIndexes`.
- Меняется поведение: индексы в новых базах не создаются; режим сброса — `NORMAL`.
- Базы прежней версии открываются и дополняются.

## Проверка

Тесты `Tests/Cases/TestSqlite.mqh` (13 случаев): строки и столбцы, счётчик, пакет без ошибок SQL, переключение
режимов, обновление старой таблицы, сохранность `_LastError`, индексы по требованию, два обработчика на базе,
режим сброса. Замер готового обработчика: по записи — 150 мкс (было 1 900), пакет 100 — 37 мкс (было 63),
`SetDurable(true)` — 1 580 мкс. Профиль `DEBUG` после `array out of range` — 6 записей из 6 в базе.
