# LOG-GAP-02: Выключенное логирование стоит времени

**Статус:** закрыт (07.10.2026)  ·  **Дата:** 2026-10-07  ·  **Находки:** F-15, F-16, F-17, F-32  ·  **Задачи:** LOG-BL-05, LOG-BL-12

## Что нужно

Советник с подробным логированием должен в оптимизации работать почти так же быстро, как без него: выключенный
уровень — одна проверка, без построения строки.

## Что есть (замеры 07.10, среднее по 200 000 вызовов)

| Вызов | Время |
|---|---|
| `logger.Log(LOG_TRACE, StringFormat(...), 0, __FILE__, __LINE__, __FUNCTION__)`, уровень логгера `WARN` | 2,4 мкс |
| то же, профиль `PERFORMANCE` | 3,4 мкс |
| то же, но под `if(logger.IsEnabled(LOG_TRACE))` | 0,01 мкс |
| `LOGTRACE_N("имя", "x")`, 25 логгеров в фабрике | 5,4 мкс |

- Строка сообщения строится у вызывающего до того, как логгер проверит уровень (F-15).
- Профиль `PERFORMANCE` ставит уровень логгера `TRACE`, а отсекает обработчик: запись создаётся и доходит до него (F-16).
- Макросы находят логгер перебором реестра со сравнением строк — на каждом вызове (F-17).
- Потребители пишут в указатель `m_logger`, макросов для указателя нет: 376 вызовов по 150–250 знаков, ни одной
  проверки `IsEnabled` (F-32).

## Пробел

Нет способа записать вызов коротко и так, чтобы выключенный уровень ничего не стоил. Профиль «для оптимизации»
медленнее обычного логгера с уровнем `WARN`.

## Варианты

1. Макросы для указателя с проверкой уровня: `LOG_DEBUG_TO(m_logger, StringFormat(...))` раскрывается в
   `if(p != NULL && p.IsEnabled(LOG_DEBUG)) p.Log(...)` — аргумент не вычисляется.
2. В профилях уровень логгера = наименьший из уровней обработчиков.
3. Макросам `LOGINFO(...)` — указатель на логгер `default`, сохранённый в фабрике (без поиска).
4. Сборка без логирования вовсе (`#define LOGGER_DISABLED` → макросы пустые) — для чистовой оптимизации.

## Предложение

1 + 2 + 3; вариант 4 — после них, если замер на реальном советнике покажет, что нужно.
